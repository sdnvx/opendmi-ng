= To do

== Vendor-specific decoders

Vendors put structured data into generic SMBIOS structures using their own
undocumented conventions. Decoding it is not done by other tools, so it is a
distinctive feature of the project. Each convention needs reverse engineering
on a representative set of dumps before a decoder can be written.

=== Dell OEM strings (type 11)

Dell systems report keyed values in OEM strings. The first string is the
marker `Dell System`, and the following strings have the form `N[value]`,
where `N` is a decimal key and `value` is its value.

Examples from the dumps in `data/dell`:

[cols="1,3", frame=ends, grid=rows]
|===
| Dump | OEM strings

| `g15-5510.bin`
| `Dell System`, `1[0A64]`, `3[1.0]`, `12[www.dell.com]`, `14[1]`, `15[0]`,
  `27[34716449091]`

| `poweredge-1800.bin`
| `Dell System`, `5[0000]`
|===

Meaning of the keys is not documented. Unconfirmed guesses:

* `1` looks like the platform System ID.
* `27` looks like the Express Service Code, i.e. the numeric form of the
  Service Tag.

To do:

* Collect OEM strings from more Dell dumps and compare keys across models
  and generations.
* Look for public sources describing the keys, e.g. Dell `libsmbios`.
* Decode the keyed values in the `dell` module, keeping unknown keys as raw
  values.

=== Module selection

Done: the platform (`dmi_platform_t`) is told from types 0 and 1, including
the family and the generation of HP and HPE servers, and the modules of the
platform are enabled as the context is opened. Modules of the structures
any platform may carry, e.g. `intel`, yield their types to the modules of the
vendors, and vendors relocate or suppress them.

The vendors of the firmware, the system, the baseboard and the processors
are told apart, and the `intel` module is enabled for the platforms of Intel
processors only.

Left:

* Recognize more system and baseboard vendors (ASUS, ASRock, Gigabyte, MSI,
  Supermicro), once their modules have structures to decode.

=== Other Intel platform structures

Found on the same set of firmware vendors, not decoded by dmidecode:

* Done: type 219 (`$MEI`, type 203 on Dell), decoded as `intel-mei`, with
  HFSTS1 and HFSTS3 of the first interface. Left: HFSTS6 (Boot Guard), whose
  layout depends on the ME generation, which FVI or `vPro` tell. Layout:
  strings `MEI1` to `MEI4`: version
  (BYTE, 1), count (BYTE), then 25-byte records of a name (STRING) and the six
  firmware status registers HFSTS1 to HFSTS6 (DWORD each) of the HECI
  function. All bits set mean that the function is absent. Bits 4 to 6 of
  HFSTS3 are the SKU (2 consumer, 3 corporate), which matches the version
  string of `ME Firmware Version` in all dumps; HFSTS6 tells the Boot Guard
  state, laid out differently in different ME generations.
* Done: type 222 (`intel-svt`, type 206 on Dell). Layout: version
  (BYTE), unknown WORD `0x0099`, count (BYTE), then milestone code (BYTE) and
  name (STRING) pairs.
* Done: type 131 (`vPro`), decoded as `intel-vpro`, told by its signature
  from Lenovo `TVT-Enablement` (`lenovo-tvt`) in the same table. Left: the
  meaning of the three flag words, and type 131 `BOOTINF` of ThinkPad T61p.
  Layout, offsets of the body: `vPro` signature at 0x34, MEBx version at 0x04
  (four WORDs), PCI device/function of the LPC bridge and its device ID at
  0x0C, ME firmware version at 0x18 (WORDs of minor, major, build and hotfix,
  as the ME reports it), PCI device/function of the Gigabit Ethernet
  controller and its device ID at 0x20, capability bits at 0x00, 0x14, 0x30.
* Done: type 130 (`intel-amt`), told by its signature. Left: the OEM
  capabilities and the last 4 bytes of the longer variant. Layout: AMT supported/enabled, IDE-R, SOL and
  network flags, a `0xA5` marker and OEM capabilities, as in the Intel AMT
  BIOS writer's guide.
* Done: type 14 groups `$MEI`, `Firmware Version Info` and `Intel(R) Silicon
  View Technology` are the groups of the `intel` module, which the
  `group-assoc.member` lint rule checks the members of. The only report in the
  corpus is `neousys/nuvo-7000-a2-cfl-s.bin`, whose `$MEI` group lists an
  FVI structure.

=== AMI specifics

Not decoded by dmidecode, reverse engineering to be finished:

* Type 133, 44 bytes, with identical content on ASUS and Gigabyte boards
  (`asus/prime-h610m-r.bin`, `gigabyte/b760m-ds3h-gen5.bin`).
* Type 136, 8 bytes of zeroes on the same boards (Lenovo has a different
  6-byte type 136).
* Additional information (type 40) used as key-value storage: values are
  always 4 bytes regardless of the referenced field size, and strings are
  e.g. `PRODUCT_LINE`, `PRODUCT_SKU`, `YEAR`, `AGESA!V9 ComboAm5PI 1.2.0.3g`.
  References point to the header (offset `0x01`), beyond the structure end,
  and to missing structures.

Other vendors misuse type 40 too: Lenovo, Toshiba and Neousys store the
compiler version in firmware information, and apply a slot type entry to port
connectors; Supermicro stores 17-byte blobs with `_AST` signature (probably
ASPEED BMC data) at offset `0x00`.

== Ideas

=== Linux kernel module

A kernel module exposing decoded SMBIOS data in sysfs, e.g. one directory per
structure with one file per attribute, built from the same decoders as
`libopendmi`.

Linux already provides:

* `/sys/firmware/dmi/tables/DMI` and `smbios_entry_point` with the raw table
  and entry point, which are read by the `sysfs` backend;
* `/sys/firmware/dmi/entries/<type>-<instance>/` with raw data of each
  structure and a few header fields;
* `/sys/class/dmi/id/` with a dozen decoded fields of firmware, system,
  baseboard and chassis information.

Decoded attributes of all structures would make SMBIOS data available to
scripts and tools without any user-space library, as `/sys/class/dmi/id` does
for a few fields. To be considered:

* Decoders use libc and `dmi_alloc()`, so they need a thin portability layer
  for kernel allocation, strings and formatting.
* License of the module (e.g. `Dual BSD/GPL`), since BSD-3-Clause code is
  compatible with GPL.
* Layout and stability of the sysfs interface, since it becomes a kernel ABI
  once merged, and whether to target mainline or ship an out-of-tree module.

== Incomplete decoders

To be closed in 0.5. Standard structures, which are not decoded completely:

* Processor additional information (type 44): processor-specific data is
  kept as raw bytes. Its format needs to be checked against the RISC-V SMBIOS
  specification, and documents for other architectures are to be found: the
  only data seen in dumps are placeholders of AMI firmware.
* Management controller host interface (type 42): only network host interface
  data and Redfish over IP records are decoded (DSP0270). Interface data of
  MCTP interfaces and records of other protocols are kept as raw bytes, since
  their formats are not defined by the SMBIOS specification.

Other standard structures are decoded completely, and bytes left in some
dumps are firmware quirks: padding in baseboard information of IBM x3950 M2,
odd length of onboard devices information of Acer Nitro, extra bytes in
management device information of Supermicro X10DDW-i.

Module structures without decoders:

* Dell BIOS flags (type 177): the structure is not described in public
  sources (`libsmbios` does not describe it either), and there are no dumps
  containing it.

Module structures are decoded and described in the reference manual
(`reference/src/specs`) according to these sources:

* Dell: `libsmbios` (`src/include/smbios_c/obj/token.h`).
* Intel RSD: Intel RSD Firmware Extension Specification v2.3.2
  (document 337201-003US).
* Sun: illumos (`usr/src/uts/common/sys/smbios_impl.h`). Device types of
  extended ports are not described there.

== Variant attributes

Values, which representation depends on other fields, are described by
variant attributes (`DMI_ATTRIBUTE_TYPE_VARIANT`): the decoder or the link
handler sets a selector, and `dmi_attribute_resolve()` returns the attribute
describing the value.

Converted: firmware inventory versions and identifiers (type 45), TPM
firmware version (type 43), management controller interface data and protocol
records (type 42), IPMI base address and register details (type 38),
management device thresholds (type 36, selector is set by the link handler of
type 35), system event log access method address (type 15) and processor ID
(type 4).

Candidates, which are not decoded yet, so that new decoders are needed first:

* Processor additional information (type 44): processor-specific data
  depends on the processor architecture, see incomplete decoders.

Intel RSD network card address is not a candidate: the structure has no field
telling the address type, see `DMI_ATTRIBUTE_FLAG_MAC`.

Open questions:

* Whether to show the selected variant in JSON, YAML and XML output, since the
  value shape of such attributes depends on the variant.

== Lint

The `lint` command is a stub: `opendmi/src/command/lint.c` only parses the
`-A` and `-l` options and reports that it is not implemented, and the man page
is empty.

Design questions to settle first:

* Where checks live: in the library, as a `check` handler in
  `dmi_entity_spec_t` next to `decode` and `link` plus a registry pass, or in
  the CLI only.
* How findings are collected: the error queue is limited to
  `DMI_ERROR_MAX_DEPTH` entries and mixes causes, so a separate list of
  findings (handle, check code, severity, message) is probably needed.
* How findings are reported: plain lines with an exit code, or through the
  output formats used by `show` and `export`.
* How checks are selected: check codes, severities, and whether warnings can
  be treated as errors.

=== Management device thresholds (type 36)

Most dumps carry template values instead of real thresholds: every field holds
its own ordinal number (`1`, `2`, `3`, `4`, `5`, `6`), and the numbering
continues across structures of the same table (`7`, `8`, `8`, `10`, `11`, `12`,
then `13` to `18`), with an obvious typo in the second set. The same set is
repeated for components of different kinds — voltage probe, temperature probe
and cooling device — although thresholds are measured in units of the
component, so the values cannot be real.

This is 52 of 66 structures in dumps of ASUS, ECS, Gigabyte, Lenovo, MSI and
Supermicro, so the source is shared firmware code rather than a single vendor.
The remaining 14 structures are filled correctly, with all fields set to
`0x8000` (threshold is not applicable).

[cols="3,1", frame=ends, grid=rows]
|===
| Check | Severity

| Thresholds repeat the ordinal numbers of their fields
| Warning

| Lower threshold is greater than the corresponding upper one, unless either
  is unspecified
| Warning
|===

== Documentation

=== Custom `@error` command

Header comments list errors raised by a function with one tag per error code:

----
 * @error DMI_ERROR_OUT_OF_MEMORY Memory is exhausted.
----

The command is not standard: Doxygen provides `@throw`, `@throws` and
`@exception` for exceptions only, and they are reserved for the C++ API. It has
to be registered once the tools are enabled:

* Doxygen: add an alias to the Doxyfile, e.g.
  `ALIASES += "error{1}=@par Error \1:"`, or render the errors as a list.
* Clang: pass `-fcomment-block-commands=error` if `-Wdocumentation` is
  enabled, otherwise the command is reported as unknown.

== Firmware quirks

=== Off-by-one handles in management device components (type 35)

Some AMI firmware reports wrong handles in management device component
structures. Field offsets match the specification, and dmidecode reads the same
values, so this is a firmware bug. Such structures fail linking: the component
handle refers to a management device (type 34) or to the previous management
device component (type 35), and the threshold handle refers to a probe or a
cooling device.

All management device components are affected in these dumps:

[cols="2,1,2,1", frame=ends, grid=rows]
|===
| Dump | SMBIOS | Firmware | Components

| `asus/rs300-e8-rs4.bin`
| 2.7
| 2101, 04/20/2018
| 5

| `ecs/x79r-ax.bin`
| 2.7
| 4.6.5, 12/04/2013
| 13

| `supermicro/x10ddw-i.bin`
| 3.0.0
| 3.4, 10/18/2021
| 13

| `supermicro/x10sll-f.bin`
| 2.7
| 3.2, 05/14/2018
| 5
|===

Other AMI firmware in `data/` is not affected: `asus/prime-h610m-r.bin`,
`asus/rs300-e11-rs4.bin`, `asus/zenbook-ux425ja.bin`,
`gigabyte/b560m-ds3h-v2.bin`, `gigabyte/b760m-ds3h-gen5.bin` and
`msi/modern-15-a10m.bin`.

Structures are grouped as a probe or a cooling device, its threshold data
(type 36) and the management device component. Example from
`asus/rs300-e8-rs4.bin`:

[cols="1,1,1,1", frame=ends, grid=rows]
|===
| Handle | Type | Component handle | Threshold handle

| `0x0036` | Voltage probe (26) | |
| `0x0037` | Threshold data (36) | |
| `0x0038` | Component (35) | `0x0035`, should be `0x0036` | `0x0036`, should be `0x0037`
|===

Findings:

* The actual component is always at the reported component handle plus one
  (36 of 36 structures in all four dumps).
* The reported threshold handle plus one is always threshold data (type 36),
  and matches the grouping above in 28 of 36 structures. The remaining 8 refer
  to threshold data of another group, and sometimes two components refer to
  the same one (e.g. `0x0059` and `0x005c` in `ecs/x79r-ax.bin` both refer to
  `0x0055`), so thresholds may be shared between components.

To do:

* Check whether the 8 thresholds, which do not match the grouping, are shared
  between components of the same kind, e.g. by comparing probe types and
  threshold values.
* Collect more dumps of the same firmware generation to find out which AMI
  versions are affected.
* Consider a workaround in relaxed mode: if the component handle refers to
  type 34 or 35, the handle plus one is a probe or a cooling device, and the
  threshold handle plus one is threshold data, use the corrected handles and
  log a notice. Strict mode and `lint` should keep reporting the errors.

=== Processor ID

* `asus/c60m1-i.bin` and `asus/k53u.bin` (AMD Bobcat) store feature flags
  before the signature. The decoder swaps the words back, since reserved bits
  of the signature are set in feature flags.
* `foxconn/m61pmv.bin` reports AMD Athlon 64 X2 with family `0x13`, which was
  Cyrix M2 in older specification versions and is Apple M2 now. Families
  `0x12` and `0x13` are treated as Arm only if the vendor or version names
  Apple.
* `honor/magicbook-art-14-2024-mra-7211.bin` reports Intel Core Ultra 7 155H
  with 80486 family. The signature is still valid, since 80386 and 80486
  families are decoded as x86.
* Several dumps report x86 processors with other or unknown family, which are
  recognized by vendor or version names.

=== TPM device vendor ID

Lenovo ThinkCentre M70s, M720q and M720s store TPM vendor ID as a
little-endian double word (`\0XFI` instead of `IFX`). The decoder reverses
the bytes, if the identifier starts with zero.
