= OpenDMI: Coding conventions

== Formatting

=== Spacing and braces

* Indent using four (4) spaces. Do not use tabs for indentation.
* Use no space between `*` and the variable name in pointer expressions (`int *foo`).
* Use space between keywords and parentheses; e.g., `if (condition)`.
* Put the opening brace of a function implementation on the line after the function’s return type, name, and argument list.

== Header guards

* Use `#pragma once` in addition to include guargs in header files to avoid duplicated includes.

== Documentation comments

* Document functions with Doxygen comments (`/** ... */`) on their
declarations rather than on their definitions: on the prototypes in the
public or internal headers, or on the prototypes at the top of the source
file for static functions.

* Document macros, types and variables at file scope the same way, with a
doc comment (marked with `@internal` in source files and internal headers)
rather than with plain `//` comments:
+
[source, c]
----
/**
 * @internal
 * @brief Size the memory of a buffer grows by, which fits the data of most of
 * the structures at once.
 */
#define DMI_BUFFER_CAPACITY_STEP 128
----

* Keep plain `//` comments for the remarks on the logic of the preprocessor,
e.g. on why a macro is undefined, on a conditional block or on the order of
includes: they explain the directives rather than describe what is declared.

* Put a blank line before every doc comment, unless it opens a block, e.g.
documents the first member of a structure right after its opening brace.

* Do not put any comment right before the definition of a function. A remark
on the function as a whole, such as why it works the way it does, belongs to
the `@details` section of its doc comment. A remark on the logic of the
function belongs inside its body, next to the code it explains.

* Declare every static function with a prototype near the top of its source
file, and put the doc comment, marked with `@internal`, on the prototype:
+
[source, c]
----
/**
 * @internal
 * @brief Read a word of the version data, which is held low byte first.
 *
 * @param[in] text  Version data.
 * @param[in] index Index of the low byte.
 *
 * @return Value of the word.
 */
static unsigned dmi_hpe_version_word(const dmi_hpe_version_text_t *text, size_t index);
----
+
The definitions of static functions follow the functions of the file which
are not static, and carry no comments of their own.

* List the errors a function raises with `@error` tags, one per error code,
e.g. `@error DMI_ERROR_OUT_OF_MEMORY Buffer cannot be allocated`, rather than
in the description.

== Public API

* Mark every function and variable declared in public headers of `libopendmi` with `__dmi_api`, e.g. `__dmi_api bool dmi_open(...);` or `extern __dmi_api const dmi_module_t dmi_intel_module;`. The library is built with hidden symbol visibility, so unmarked symbols are not exported from the shared library.

== Naming

* Use `snake_case` to name a multi-word variable or type.

* Use `UPPER_SNAKE_CASE` for, and only for, preprocessor symbols and values of enumeration type.

* Use typedef to create aliases for all struct types.

* The names of type aliases should always end in `_t`.

* Function pointer type aliases should always end in `_fn`.

* Do not alias pointer types with `typedef`; we keep them explicit.

* Name boolean variables with a verb phrase including a verb like `is_`,
`has_`, or `want_` so that the intent of the variable is clear in
expressions and conditionals.

* Avoid magic numbers; define meaningful constants. Prefer C language symbols over preprocessor symbols, because the former are visible in a symbolic debugger like gdb.

=== Function prefixes

* Name a function after the subsystem it belongs to: `dmi_<subsystem>_<name>`,
where the subsystem is the type the function operates on, e.g.
`dmi_entity_decode()`, `dmi_registry_lookup()`, `dmi_attribute_format()`,
`dmi_reader_skip()`.

* Within a subsystem, name a function that returns a property of its object
after the property itself, without a verb: `dmi_entity_buffer()`,
`dmi_entity_context()`, `dmi_attribute_resolve()`. The prefix already tells
what the function operates on, so there is no ambiguity.

* Functions of the DMI context are the only ones without a subsystem prefix,
because the context is the root of the API: `dmi_create()`, `dmi_open()`,
`dmi_load()`. Their names must start with a verb (`create`, `open`, `close`,
`destroy`, `get`, `set`, `add`, `has`, `find`, `load`, `save`), so that they
are not read as the beginning of a subsystem family. A name starting with a
noun is not allowed there: `dmi_registry()` reads as a function of the
`dmi_registry_*` family rather than as the registry of a context, hence
`dmi_get_registry()`.

* Use `get` and `set` only in pairs and only for context functions, e.g.
`dmi_get_flags()` and `dmi_set_flags()`. Elsewhere `get` means a lookup and
should be named accordingly: `dmi_registry_lookup()`, `dmi_name_lookup()`.

=== Error codes

* Name an error code `DMI_ERROR_<SUBJECT>[_<DETAIL>]_<CONDITION>`, where the
subject is the noun the API uses for what went wrong, e.g. `ARGUMENT`,
`FILE`, `ENTRY`, `ENTITY`, `MODULE`, and the condition is one of `NULL`,
`INVALID`, `UNKNOWN`, `NOT_FOUND`, `TRUNCATED`, `DUPLICATE`, `CONFLICT` and
`UNAVAILABLE`, e.g. `DMI_ERROR_ENTRY_CHECKSUM_INVALID`.

* Name the failure of an operation `DMI_ERROR_<SUBJECT>_<VERB>_FAILED`, e.g.
`DMI_ERROR_FILE_OPEN_FAILED`, so that a verb is not read as a condition.

* Only the general errors have no subject: `DMI_ERROR_NONE`,
`DMI_ERROR_INTERNAL`, `DMI_ERROR_SYSTEM` and `DMI_ERROR_OUT_OF_MEMORY`.

* Check the arguments of a function with explicit conditions, and report
their errors with the macros of `<opendmi/trace.h>`, which raise the error
and evaluate to the value the function returns:
+
[source, c]
----
if (path == nullptr)
    return dmi_trace_argument_null(context, path);
----
+
Leave a check silent only where `nullptr` is a valid value rather than an
error, e.g. a missing filter matching everything. The functions of the error
queue itself check their arguments silently, since they cannot raise errors.

* The code name of an error is its name in lower case with dashes, e.g.
`entry-checksum-invalid`, which is also the key of its translation.
